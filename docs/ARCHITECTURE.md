# Architecture

This document captures the architectural decisions that shape the codebase. Update it whenever you make a decision that affects future work — do not silently change shape.

## North star

The platform is **multi-tenant B2B lead discovery and outreach**. The unit of tenancy is the **Workspace**. Everything tenant-owned — users, products, connectors, harvested records, drafts, learning memory — belongs to exactly one workspace.

The system must remain useful even when AI and search providers are disabled. AI is an **assistant layer**, not the foundation.

## Stack decisions

| Database | PostgreSQL | Boring, reliable, strong text search, JSONB for flexible payloads, good at relational + semi-structured |

| Auth | Auth.js (next-auth v5) | Built for Next.js, OAuth-ready, session storage in DB |
| Background jobs | Abstraction layer; in-memory in dev, BullMQ + Redis later | Isolate the queue from the rest of the codebase so swap is cheap |
| File storage | Abstraction layer; local FS in dev, S3-compatible later | Same reason |
| AI providers | Abstraction layer; mock + real implementations | Required by the brief: app must run without paid AI |
| Search providers | Abstraction layer; mock + real implementations | Same |
| Tests | Vitest | Native ESM, fast, plays well with Next.js + Drizzle |
| Browser smoke tests | Playwright (`e2e/`, `pnpm test:e2e`) | Every route at 1440px and 390px against a running app seeded by `scripts/seed-demo.ts`: status < 500, no uncaught page errors, no sideways scroll on a phone. ## Workspace-first

This is the most important rule and the most often violated. Two stances:

1. **Every tenant-owned table includes `workspaceId`** as a NOT NULL column with an index. Tables that are *not* tenant-owned (e.g., the `users` table — users can belong to multiple workspaces) are explicitly documented in `docs/DATABASE_MODEL.md`.
2. **Every service function takes `WorkspaceContext` as its first argument.** There is no global default workspace, ever. There is no "service-level" code that runs without a workspace context — even cron jobs and connector runs carry an explicit `workspaceId`.
3. **The super-admin console is the one exception, and it uses `PlatformContext`, never `WorkspaceContext`.** `requirePlatformAdmin()` (`src/lib/services/auth-context.ts`) returns `{ scope: 'platform', actorUserId }` with no workspace in it. Platform services (`admin.ts`, the platform half of `users.ts`, support admin, `adjustTokens`, platform keys and settings) take it first, plus an explicit target workspace id wherever they touch a tenant. They audit either at platform scope (`workspace_id` NULL: users, pre-authorisations, platform roles, keys, settings) or against that explicit target (billing, tokens, members, support replies) — never against the workspace the admin's switcher points at. Nothing under `src/app/admin` may call `getWorkspaceContext()`; a static test (`src/tests/admin-console-static.test.ts`) enforces it. That includes the `/admin/providers` live checks ("Test platform AI default" and each vendor's "Test key"), which since PC-02 test only the platform tier (console key, else env var) and never resolve a workspace. `PENDING_EXCEPTIONS` in that test is empty; an entry may only be added with the change that removes it.

Workspace-isolation tests run on every CI build. They are the only tests that can never be skipped or marked as TODO.

## Module boundaries

Modules are **vertical slices** of the domain, each owning a set of tables, a service layer, types, and tests. Modules talk to each other only through their public service API — never by reaching into another module's tables directly.

The dependency graph is intentionally shallow:

```
auth, workspace            <-- foundation, depended on by everything below

product_profile            <-- depends only on workspace
connector_framework        <-- depends on workspace
search_provider            <-- depends on workspace, used by connectors
ai_provider                <-- depends on workspace (for usage logs); used by classification, drafts, learning
source_record              <-- depends on workspace + connector_framework
qualification              <-- depends on source_record + product_profile + (optional) ai
review_queue               <-- depends on source_record + qualification
draft                      <-- depends on review_queue + product_profile + (optional) ai
learning                   <-- listens to review_queue + draft, feeds qualification + draft
audit_log, usage_log       <-- written by everyone, read by admin views
```

Cross-cutting modules (audit, usage, jobs, storage) are accessed via interfaces, not direct imports of business modules.

A full module-by-module description is in `docs/MODULES.md`.

## Provider abstractions

Four kinds of pluggable providers, each defined by a TypeScript interface with a small surface and a mock implementation that ships in the repo.

### `IAIProvider`
```ts
interface IAIProvider {
  id: string;
  generateText(input: AIGenInput, options?: AIGenOptions): Promise<AIGenResult>;
  generateJson<T>(input: AIGenInput, schema: ZodSchema<T>, options?: AIGenOptions): Promise<T>;
  estimateCost(usage: AIUsage): number;
  healthCheck(): Promise<{ ok: boolean; detail?: string }>;
}
```
Active-provider resolution (all capabilities, see `src/lib/services/provider-settings.ts`): workspace setting → env selector (`AI_PROVIDER` etc.) → **auto-detected system default** — the first vendor whose platform key env var is set (`systemDefaultProvider`). `mock` is a dev/test tool only: it returns deterministic stubs, is never offered in the customer UI, and in production a capability with no platform key resolves to the preferred real vendor so calls fail loudly ("no key configured") instead of fabricating mock data. Vector storage defaults to `pgvector` (keyless).

**Setup modes** (chosen in onboarding, stored on `workspaces.setup_mode`): `simple` = the workspace runs on the platform's system keys/defaults and `/settings/integrations` is a read-only summary; `advanced` = same defaults but provider selection and BYOK keys are editable. Switching to simple resets provider-selection overrides to NULL (BYOK secrets are kept). NULL setup_mode (legacy workspaces) behaves as advanced.

### `ISearchProvider`
```ts
interface ISearchProvider {
  id: string;
  search(query: string, options?: SearchOptions): Promise<SearchResult[]>;
  testConnection(): Promise<{ ok: boolean; detail?: string }>;
  estimateUsageCost(query: string, options?: SearchOptions): number;
}
```
The mock provider returns a fixed result set keyed off the query string — enough for end-to-end tests of the connector + review pipeline without hitting SerpAPI.

### `IJobQueue`
```ts
interface IJobQueue {
  enqueue<P extends JobPayload>(type: JobType, payload: P, options?: JobOptions): Promise<JobId>;
  status(id: JobId): Promise<JobStatus>;
  cancel(id: JobId): Promise<void>;
  on(type: JobType, handler: JobHandler): void;
}
```
In-memory implementation in Phase 1 — handlers run inline on a microtask. BullMQ implementation later for production durability.

**Outbox, not queue retries (KL-03).** The queue adds no attempts of its own, so durable background work keeps its state in the database: the request writes the work as rows in the same transaction as the change, enqueues a job after the commit (best effort), and a repeatable sweeper re-enqueues what was lost, retries failures with backoff and releases stale claims. The learning layer works this way (`learning_events` outbox, `learning.process` + `learning.sweep`, see [`LEARNING_LAYER.md`](LEARNING_LAYER.md)), and so does knowledge indexing (KL-06: `indexing_jobs` outbox, `knowledge.index` + `knowledge.index.sweep`, `services/knowledge-indexing.ts`); the sweepers only enqueue, so they behave the same on the memory queue and on BullMQ. No extraction, OCR, embedding or AI extraction runs inside an operator's request (I108).

### `IStorage`
```ts
interface IStorage {
  put(key: string, body: Buffer | Readable, meta?: StorageMeta): Promise<void>;
  get(key: string): Promise<Readable>;
  delete(key: string): Promise<void>;
  signedUrl(key: string, options?: SignedUrlOptions): Promise<string>;
  exists(key: string): Promise<boolean>;
}
```
Local-filesystem implementation (`STORAGE_PROVIDER=local`, used in production today) and an S3-compatible one (Hetzner Object Storage / B2 / Wasabi / R2 / MinIO). `get()` rejects with `StorageObjectNotFoundError` when the key holds nothing.

**Browsers never get a storage URL.** Workspace files go out through authenticated route handlers: they resolve the `WorkspaceContext`, let the owning service find the object inside that workspace, and return `storageDownloadResponse()` (`src/lib/storage/download.ts`: attachment, sanitised filename, `Cache-Control: private, no-store`, `nosniff`). Today those routes are `GET /api/documents/[id]/download` (`streamDocument`, any workspace role) and `GET /api/crm/exports/[file]` (`streamCsvExport`, write roles). A key in another workspace answers 404, the same as a missing one. `LocalFileStorage.signedUrl()` throws `StorageUrlUnavailableError`, because a `file://` path cannot be opened by a browser. S3 presigned URLs stay available for future server-to-server use, but pages do not link to them: a presigned link works for anyone who holds it and carries the UUID key as its filename.

## API design

- Route handlers live under `src/app/api/<resource>/route.ts`. They are thin: parse input → enforce auth + workspace context → call service.
- Services live under `src/lib/services/<module>/`. They take a typed `WorkspaceContext` as first arg.
- Validation: Zod schemas at the API boundary. The service layer trusts its inputs (it has been validated and authorized).
- Errors: services throw typed errors (e.g., `WorkspaceAccessDenied`, `ProductProfileNotFound`); route handlers translate them into HTTP responses.
- Server (form) actions translate the same typed errors into a readable `?error=` / `?message=` flash with `describeActionError(err, [XxxServiceError, …])` from `src/lib/action-errors.ts`, which rethrows Next redirect/notFound throws and anything not listed. Each action decides what `not_found` / `conflict` mean for it (a repeated "end session" is a success; "connector inactive" is not). Unexpected errors fall through to the branded error boundary: inside the workspace frame `src/app/(app)/error.tsx` (and `(app)/not-found.tsx` for a workspace page's `notFound()`), so the header and sidebar stay on screen; elsewhere `src/app/error.tsx` (root-layout failures to `global-error.tsx`; unknown URLs to `not-found.tsx`). Prefer module-scope actions in a `'use server'` file bound with `.bind(null, id)` — they are testable and cannot close over page-local helpers.

## Auth + session

- Auth.js with Google OAuth as the only provider initially. Adding GitHub or email/password later is one config change plus tests.
- Sessions stored in the database (Drizzle adapter), not JWT. Reasoning: workspace switching, role changes, and immediate revocation work cleanly with DB sessions.
- Each session row carries its own workspace (`sessions.activeWorkspaceId`, MOB-06): a new sign-in starts in the user's last-used workspace (`users.activeWorkspaceId`), else their oldest membership, and is pinned there on its first request; every request resolves `WorkspaceContext` from the session the request cookie names. The session callback returns only the user and the expiry, never the session row (its token and bigint columns).
- The first user whose email matches `OWNER_EMAIL` becomes `super_admin` automatically. There is no other path to that role in Phase 1.

## Multi-workspace per user

A user can belong to multiple workspaces. The `workspace_members` table joins them with a role (`owner | admin | manager | member | viewer`). Switching workspaces (the header switcher) updates the switching session's row and the user's last-used value; the user's other sessions (another browser, a phone) stay where they are. Tabs of one browser share a session, so actions that send, spend or decide carry the workspace their page was rendered for and are refused (`workspace_changed`) after a switch in another tab — see the MOB-06 decision below.

## Audit and usage logs

Two append-only tables, both indexed by `(workspaceId, createdAt)`:

- **`audit_log`** — significant user-visible actions (workspace created, member invited, lead approved, draft generated, settings changed, ...).
- **`usage_log`** — provider calls and resource consumption (search queries, AI calls, jobs, storage bytes, ...).

These tables are written by every relevant module and read primarily by admin views and cost dashboards. They are not a debugging log — that's stdout/journal.

## What we are not building yet

These are explicitly out of scope until later phases (see `docs/ROADMAP.md`):

- Email sending and IMAP sync.
- Vector search and RAG.
- CRM integrations.
- Billing.
- Super admin / God Mode UI.
- Real connector implementations beyond mock + CSV.

Each of these has a hook in the data model so it can be added without rewriting Phase 1 code. The hooks are documented in `docs/MODULES.md`.

### 2026-05-01 — Phase 0 stack lock-in
**Decision:** Next.js + Drizzle + PostgreSQL + Auth.js + Vitest + Docker.
**Reasoning:** Boring, well-supported, single-language stack. Hetzner-friendly. Drizzle was preferred over Prisma for lower magic and easier migrations. PostgreSQL was preferred over MySQL/TiDB despite recent experience with TiDB Cloud — Postgres has stronger full-text search, better JSONB support for the connector raw_data column, and is easier to self-host.
**Alternatives rejected:** Prisma (heavier runtime, harder migrations on existing DBs); Hono (lighter than Next.js but means picking + integrating a UI framework separately); SQLite (won't scale to thousands of harvested records cleanly with concurrent connector runs).

### 2026-10-01 — PlatformContext for the super-admin console (PC-03)
**Decision:** Console pages and their server actions get a `PlatformContext` from `requirePlatformAdmin()` instead of a `WorkspaceContext` from `getWorkspaceContext()`. Platform services reject anything that is not a `PlatformContext` (including a `WorkspaceContext` with role `super_admin`) and take an explicit target workspace id. The no-op "Impersonate" control and its service path were removed; `impersonation_sessions` stays as history.
**Reasoning:** A `WorkspaceContext` in the console resolves to whatever workspace the admin switcher points at. Every console action was therefore audit-logged into that workspace — in god mode a tenant the admin does not belong to — and that tenant's admins could read other customers' emails, names and suspension reasons on `/settings/audit` (I051). Impersonation recorded sessions that nothing ever applied (I047). Rows already misfiled are moved by `scripts/remediation/refile-platform-audit.ts` (dry run by default; apply only with the fingerprint of a reviewed dry run; reversible through `payload.refiledFrom`).
**Alternatives rejected:** Keeping `WorkspaceContext` and passing the real target alongside it (the ambient workspace would still be one typo away); making impersonation real now (it needs a design for a read-only, time-boxed identity overlay first — PC-18).
### 2026-10-01 — Inbound relevance gate before the reply pipeline (Phase 0, flow:F-01)
**Decision:** Every IMAP-synced message is stored and threaded, but only messages proven to be about our outreach enter the reply pipeline. At parse time `lib/mail/relevance.ts` captures header signals (List-*, Precedence, Auto-Submitted, ESP markers, the parsed delivery-status report) and stores headers JSON-safely; `services/inbound-relevance.ts` adds DB facts (a reference to one of OUR outbound Message-IDs, matched case-insensitively; a DSN about our mail; a contacted lead's address; our own mailbox) and the pure decision labels `mail_messages.outreach_relevance` as prospect_reply / auto_reply / bounce / bulk / unrelated. Only the first three are classified (on the sender's own words: quoted history and our footer stripped) and may cause side effects; automatic suppression additionally needs a prospect_reply, and bounce suppression is off until DSN-based bounce handling (F-32).
**Reasoning:** The classifier ran over every synced email; newsletter footers read as unsubscribes and suppressed ~141 innocent addresses, created ~221 junk contacts, 359 false "Reply from" notifications and paid for translations of junk (X1). Proof of relation (references / DSN / lead address) is cheap, explainable (stored as evidence on the row) and errs towards doing nothing.
**Alternatives rejected:** Thread membership as proof (subject-fallback threading merges unrelated conversations, I008 — revisit with F-34); a keyword blocklist of newsletter senders (unbounded, silently wrong); classifying everything and only filtering the auto-actions (still pollutes contacts, notifications, labels and token spend).

### 2026-10-01 — Send mode, a human-confirmed unsubscribe, and suppression only on recipient rejections (Phase 0, flow:F-05)
**Decision:** `sendMessage` takes a required `mode`. `one_to_one` (compose, thread replies, queued drafts that answer a prospect's reply) carries no unsubscribe footer and no List-Unsubscribe headers; `sequence` (cold first touches, referral intros, follow-ups) keeps both. `GET /api/unsubscribe/<token>` only renders a confirmation page (and HEAD is an explicit no-op); only POST — the page's button or an RFC 8058 one-click POST — opts out, and then also cancels queued sends, pending / awaiting-approval follow-ups and open leads for that address (`services/unsubscribe.ts`, null actor). A send error suppresses a recipient only when the server refused that recipient at RCPT TO as non-existent / disabled (enhanced 5.1.x except the sender codes 5.1.7 / 5.1.8, or 5.2.1; 550-class "user unknown" text without an enhanced code) — `lib/mail/smtp-errors.ts`; a refused login (EAUTH / 534 / 535) marks the mailbox failing (`markMailboxFailing`, one deduped `mailbox.failing` notification), and the outreach queue and follow-ups hold behind a failing mailbox instead of failing.
**Reasoning:** B2B link scanners fetch every URL in an email, so a GET that unsubscribes silently drops prospects on arrival (I012). Any SMTP error with a code used to suppress every recipient — a rotated password blacklisted up to 50 prospects per drain, permanently for 5xx (I007). Personal replies carried a bulk-mail footer (I089) and compose sent the signature twice (I090).
**Alternatives rejected:** A default mode (a forgotten caller silently gets the wrong legal footer either way); JavaScript auto-submit on the confirmation page (scanners run JavaScript); suppressing on any 5xx at RCPT (relay / policy / blocklist refusals are about us); queue backoff for every transient failure here (the full taxonomy and stored stage + enhanced code on the failure row follow in F-28).

### 2026-10-01 — Production data is repaired by versioned, reviewed, revertible scripts (Phase 0, flow:F-06)
**Decision:** Data remediation lives in `scripts/remediation/<batch>/` (first: `2026-10-funnel`, mail module) on a shared engine (`scripts/remediation/lib/`). A dry run is read-only and writes a plan with a sha256 hash, a markdown report and a `decisions.csv` (bulk categories per workspace, judgement rows one by one) into the git-ignored `remediation-reports/`. `--apply` takes the report and the owner's decisions, recomputes the plan from the database and refuses on any hash drift, then runs one transaction per category; every changed row gets a before- and after-image in `remediation_log` and every run a `remediation_runs` row (id = batch id, so a report applies once). `--revert` restores the images in one transaction and reports rows changed since the apply as conflicts. Suppressions are revoked and contacts archived, never deleted; a token credit is an opposite ledger entry on revert. Provenance that the schema never recorded (pre-F-03 suppressions) is rebuilt from `audit_log`, not from notes.
**Reasoning:** X1 wrongly suppressed ~141 addresses (including the owner's colleagues), created ~221 junk contacts and 359 false notifications. Repairing that by hand-written SQL on prod would be unreviewable and irreversible, and a note-based guess would revoke opt-outs a person had entered before the classifier touched the row. Recomputing at apply time means the owner approves exactly what runs, and the images make every step undoable byte-for-byte.
**Alternatives rejected:** A one-off SQL file (no review artefact, no revert); a data migration (runs unreviewed on deploy, cannot take per-row owner decisions); trusting the plan file at apply time (stale or edited plans would execute); before-images in a JSON file on the host (lost with the host, not transactional with the change).

### 2026-10-02 — One holds model, the automation gate and the accountable-owner rule (Phase 1, PC-06)
**Decision:** Work that can be stopped is named by capability (`sending`, `inbox_sync`, `inbound_actions`, `discovery`, `autopilot`, `crm_sync`, `background_ai`, `auto_topup`; `schema/holds.ts`). A hold (`workspace_holds`) stops either all of them (scope `all`) or a list, for automatic and manual work alike, until it is released or its optional expiry passes (the gate compares against now(), so no job has to end it). It records source (`tenant` / `platform`), reason, actor, state (`active` / `pending_review` / `released` / `discarded`) and a history; `blocks_access` is stored now and enforced from PC-21. `services/automation-gate.ts` loads one `AutomationState` per workspace (enforced holds, the platform-wide outbound stop in `platform_settings` key `outbound.stop`, and whether the owner is accountable) and a pure `decideGate(state, capability, {manual})` decides, in this order: archived (automatic only), the platform outbound stop (Sending only, manual sends too, super-admins only), holds (platform holds reported first), then the accountable-owner rule (automatic only). Every place such work starts asks the gate: `sendMessage` (every send; `automatic: true` from the drain and the follow-up tick), the drain (before each row claim), follow-ups (before each composition), `syncInbound` / `safeSyncOne`, `startRun` / Run now / the crawl tick, `runOnce` and each of its steps, the CRM pushes, compaction, synthesis, the health check's AI review, reply auto-drafting, inbound auto-translation, reply auto-actions and auto top-up. Ticks iterate `activeWorkspacesForTicks()` and skip a held workspace (counted, not an error); background work runs under `makeAutomationContext()` (acts as `workspaces.owner_user_id`, `trigger: 'automation'`). When that owner is not active or no longer a member, automatic work stops with `no_accountable_owner` — no fallback to another member — and the first gate to see it raises one incident (an audit row plus an admin notification; `workspaces.automation_owner_incident_at` makes it exactly once per episode) until PC-07's incident stream. Feature flags are replaced: the console writes holds, and `scripts/remediation/import-legacy-feature-flags.ts` imports disabled flags as `pending_review` rows the platform owner confirms or discards (never enforced before that).
**Reasoning:** The console's feature flags were never read (I048): a disabled `mailbox.imap_sync` stopped nothing and workspace 2 kept syncing (X6). Suspending an owner stopped their sign-in but not their workspace's automation, which kept acting in their name (I049). Stops existed only per feature and per page (I004). One model with one gate makes "is anything held?" answerable in one place, testable as a truth table, and visible to tenants on one banner.
**Alternatives rejected:** Enforcing the legacy flags as they were (they had never had any effect, so enforcing them on deploy would have stopped live tenants without anyone deciding it); a fallback to another admin when the owner is gone (automation would act in the name of someone who never accepted that); a stop only at the ticks (manual paths and in-flight loops would bypass it — the gate sits in the services); a Postgres view for the state (kept as one TS loader of three queries until PC-05 adds the pause to the same state).

### 2026-10-02 — One workspace pause, per-item gate re-checks, the go-live hold and the wallet gate (Phase 1, PC-05)
**Decision:** The automation gate (`services/automation-gate.ts`) decides from one `AutomationState` per workspace, read from the Postgres view `workspace_automation_state` (lifecycle, accountable owner, the workspace pause `workspaces.automation_paused_*`, the go-live hold `workspaces.outreach_live_at`, the wallet and the plan columns) plus the enforced holds and the platform outbound stop. `decideGate(state, capability, {manual, origin, mailboxStatus, spendsTokens, confirmPaused})` stays pure and adds, after PC-06's checks: the pause (every automatic capability but `inbox_sync`; a manual send only with a confirmed "send anyway", which `sendMessage` audits as `outbound.override` before it sends), the autopilot plan, the go-live hold (origins `cold`, `follow_up`, `ai_reply` held until a super-admin releases the workspace — `services/go-live.ts`, audited against the tenant; `manual` mail never held), the mailbox (automatic work on a paused / failing / archived mailbox is deferred, never failed) and the wallet. A refusal carries a scope: `workspace` stops a loop and leaves the rest untouched; `item` defers just that item (+15 min, the reason in `last_error`) and the loop goes on. Every send declares its `origin` (required on `SendMailInput`, like `mode`). Loops re-check before every item: the drain before each claim, follow-ups before each composition (and `sendMessage` before each send), `runOnce` before each step and each candidate, the crawl tick per workspace and per recipe, the IMAP tick per mailbox. The drain's claim takes `FOR KEY SHARE` on the workspace row and refuses while paused, and the pause takes `FOR UPDATE` before stamping `automation_paused_at` from `clock_timestamp()`, so no row is ever claimed (`outreach_queue.claimed_at`) after the pause time. The pause itself (`services/automation-pause.ts`): any write role pauses, never plan- or wallet-gated; the person who paused can undo within 10 s (database clock); owners and admins resume; each step is audited (`automation.paused` / `automation.pause_undone` / `automation.resumed`, with source and device). Reply auto-actions held by the pause are counted from their `reply.auto_actions_held` audit rows for the resume dialog. The two legacy `emergency_pause` columns were migrated into the pause (custom SQL in `p1_automation_control_pause`) and are now only a write-only mirror of it, dropped one release later.
**Reasoning:** Two unrelated "Emergency pause" switches each stopped only part of the work (I004, I046), could not be saved on a lapsed plan (I063) and silently switched autopilot off from `/connectors/engine` (I062); paused and failing mailboxes failed their due queue (I014, I095, P0-F08); compaction and reply drafting spent tokens with no wallet check (I110, I093). One pause in the same state the gate already reads, re-checked per item, makes "stop everything now" true within one item, and the item/workspace split lets one bad mailbox or one held origin wait without stopping the rest. The lock pair makes the "nothing claimed after the pause" guarantee hold under concurrency, not just in sequence. The owner decided inbox sync keeps reading while paused (replies still arrive; their auto-actions wait).
**Alternatives rejected:** A hold with scope `all` as the pause (it refuses manual work too and only owners/admins release a tenant hold; a pause must stop automation but leave people working); keeping per-feature pauses with a "pause everything" button that flips them all (two sources of truth again); failing deferred rows and letting operators requeue them (I014: nothing requeues them); advisory locks for the claim (awkward with the pooled client; the row lock on the workspace is enough and visible); dropping the legacy columns in the same migration (the backfill must read them, and a rollback to the old code would lose an active pause).

### 2026-10-02 — One automation policy, narrow-only product overrides and honest autopilot switches (Phase 1, PC-13)
**Decision:** `services/automation-policy.ts` is the one answer to "what runs on its own here, for which product, and why not". `resolveAutomationPolicy(ctx)` combines the gate's `AutomationState` with the configuration of every automatic path (autopilot and its per-product overlays, the send queue, follow-ups, inbox sync, reply auto-actions and drafting, knowledge compaction, the health check, the trash purge, auto top-up) into an `AutomationPolicy` with one `paths` line per path (status runs / partial / held / off, a sentence, the registered ticks that run it). It is the only reader of the autopilot step switches and of `autopilot_product_settings`; the decisions are pure (`buildAutomationPolicy`, `productPolicy`, `tickVerdict`, `describeAutomationState`, `autopilotFlow`). Every background tick iterates `workspacesForTick()` (the gate's tick list plus each workspace's policy, loaded in a fixed number of queries) and asks `tickVerdict(policy, tick)`: held by the gate (counted as `held`), off by configuration (skipped silently — autopilot off no longer writes an `autopilot_disabled` log row every 5 minutes), or run. Per-product overrides are **narrow-only**: a switch is NULL (inherit) or false (off), the threshold can only be raised (the resolver takes the higher one), and `true` is refused by the service (`widening_override`) and by a CHECK constraint. A product pause (`autopilot_product_settings.paused_at`; any write role pauses, owners and admins resume, audited, never plan-gated) means autopilot does nothing for the product, the drain and the follow-up tick defer its rows like a paused mailbox (still queued / pending, reason in `last_error`, re-read before every row), and no AI reply draft is written for its leads. `updateAutopilotSettings` gates only false→true transitions. The dead toggles are removed from code and UI (columns kept one release, zeroed): autopilot's "Auto-drain" and "Sync inbound mail" steps (the drain and IMAP ticks are the only paths) and "Auto-send replies". The Crawl Engine page shows autopilot read-only with a link. The CRM steps push only leads never pushed or changed since (correlated NOT EXISTS on `crm_sync_log` against `qualified_leads.updated_at`, a failed push retried after an hour), in id order; the deal step only sees leads whose contact is synced. `getAutomationState(ctx)` is the header pill's read model: Stopped by platform > Paused > Blocked > Autopilot on > Manual, "Partly paused", degradations, a one-liner generated from the configuration, and "What runs right now".
**Reasoning:** Three switches did nothing the operator could rely on (I019), per-product overrides were saved and shown but never applied (I020), the Crawl Engine form could switch autopilot off (I062), a lapsed plan could not save "off" (I063), autopilot's inbound sync bypassed the IMAP backoff (I067) and the CRM steps re-pushed the same 50 leads every 5 minutes (I072). One resolver makes the page, the pill and the ticks agree by construction, and narrow-only overrides keep "on" meaning one thing: the workspace runs it.
**Alternatives rejected:** Widening overrides ("on" for one product while the workspace is off — flow:F-08 allowed it; PC-13 and PC-34 chose narrow-only, which keeps the workspace switch the single place that starts automation and the migration a no-op for every existing "on" value); a new `automation_policies` table now (F-08's full design: the overlay table already holds the per-product rows, and the PC-34 /automation page is the moment to reshape storage); dropping the dead columns in this migration (a rollback's `select()` would fail; dropped one release later, like the PC-05 mirrors); a per-product pause as a workspace hold (holds are per capability, not per product, and only owners/admins release a tenant hold).

### 2026-10-02 — Autopilot selects in SQL before its cap, decides once per item, and reports step errors (Phase 1, PC-11)
**Decision:** Every autopilot candidate query filters in SQL before its LIMIT, so `maxApprovalsPerRun` / `maxEnqueuesPerRun` count only work the step will do and a backlog drains across runs. Auto-approve: the policy's per-product exclusions (switched off, paused, autopilot off) and per-product thresholds (`resolveAutomationPolicy`, the higher of workspace and product) become SQL conditions; candidates are grouped per review item (best eligible score first), so an item relevant to several products is one candidate, approved once by `autopilotApproveReviewItem(ctx, id, {runId, productProfileIds})` — conditional on the item still being `new`, origin `autopilot`, `approved_by_user_id` NULL and `approval_reason` 'autopilot', one audit row carrying the run and the products, the learning feed called once with that origin (its events carry no person and reinforce no lessons). `applyStateChange` locks the row and treats a same-state transition as a no-op (no audit row, no learning), so re-approving writes nothing. Generate + queue: `NOT EXISTS` a non-superseded draft for the pair, the product exclusions, and `EXISTS` a pipeline lead for the pair with a plausible contact email (`plausibleEmailSql`, the same two patterns as `isPlausibleEmail` bound as parameters), ordered by `approved_at`; pairs still waiting for an email get no draft and are counted as `needs_contact` in the step detail (I001). The CRM steps push with origin `autopilot`; every succeeded push (manual or automatic) writes one `pipeline_events` row (`crm_contact_sync` / `crm_deal_sync`, or a `transition` to synced_to_crm when a manual push advances the lead; no person as actor for autopilot), and a contact push reuses the last *contact* external id, never a deal's. `runOnce` tallies each step's errors (failed items, failed pushes, a step that threw — which no longer aborts the run) and reports each failing step once per run through `services/autopilot-incidents.ts` as a PC-07 `raiseOpsEvent`-shaped input keyed per workspace, step and UTC day (`autopilot:<step>:<YYYY-MM-DD>`), so the incident stream's fingerprint dedupe yields one incident per step per day with its errors as occurrences. Until PC-07 (another lane) is integrated the default sink logs each key once per day.
**Reasoning:** The candidate queries applied LIMIT before their filters with no ORDER BY (I018): once about 20 approved pairs had drafts, or belonged to an opted-out product, every run reported `enqueued=0/20` and newer approvals were never reached; an item relevant to N products was approved N times per run, each time writing an audit row and feeding learning as if the owner had decided (I034); generate + queue wrote and approved a draft before finding out the lead had no email, which then blocked that lead forever (I001). Errors only reached `autopilot_log`, which nobody reads.
**Alternatives rejected:** Joining `autopilot_product_settings` in the candidate SQL (the policy resolver is the only reader of overlays since PC-13; its resolved exclusions and thresholds are passed in); de-duplicating per item in JS after an over-fetch (GROUP BY makes the cap count items exactly); logging a `needs_contact` row per waiting pair every 5 minutes (log noise — a count in the step detail instead); auto-resolving a step's incident on its next clean run (a flapping step would open several incidents a day; the day key is the dedupe contract).
### 2026-10-02 — Job heartbeats, an incident stream and a readiness probe (Phase 1, PC-07)
**Decision:** Every handler registered with the job queue is wrapped by `instrumented(name, handler)` (`src/lib/jobs/instrumented.ts`). The wrapper writes `job_heartbeats` on start and finish (duration, status, consecutive failures, the handler's structured summary) and gives the handler a `TickIncidents`. A per-workspace failure inside a tick becomes a workspace-scope `ops_events` row (fingerprinted, deduplicated, masked) that the workspace's next success resolves. A whole-job failure is a platform-scope `tick.failed` / `job.failed`. The BullMQ worker's `failed` / `error` events raise platform incidents for anything the wrapper did not see. The schedule registration at boot stamps `registered_at` and `boot_id` per tick. `/api/ready` (503 on failure) checks the database, Redis (bullmq only), applied migrations and tick staleness. Staleness uses the expected-slot rule (epoch-aligned slots under BullMQ, registration-based under the memory queue, `pending` until the first slot after registration, a 10-minute boot grace). `/api/health` stays I/O-free.
**Reasoning:** Tick results were BullMQ return values that nothing read, per-workspace errors went only to `console.error`, the worker had no failure listener, and `/api/health` was static. A dead worker or a lost Redis therefore looked healthy while sending, sync, follow-ups and autopilot all stopped (I022). Failures that matter to an operator had no record at all (I021). Staleness is computed on read (never stored), so a stopped worker that writes nothing still turns stale.
**Alternatives rejected:** Heartbeats in a Redis hash (lost with Redis, which is exactly the failure to detect; not joinable with tenants); a fixed `interval × 3` age rule (a weekly tick right after a deploy would read stale, and a weekly tick could miss its slot for weeks); deep checks in `/api/health` (container restarts on a slow dependency); BullMQ `QueueEvents` / bull-board (another Redis-dependent moving part, and no per-workspace view).

### 2026-10-02 — Owner alerts to ntfy from an in-process watchdog (Phase 1, PC-08)
**Decision:** Owner alerts go to one ntfy topic configured in the server env (`NTFY_TOPIC` required, `NTFY_URL` default `https://ntfy.sh`, optional `NTFY_TOKEN`, `OPS_ALERT_MIN_SEVERITY` default `error`); unset means alerts off, logged once. A watchdog timer in the app process (`src/lib/ops/watchdog.ts`, every 60 s) turns a tick that is stale on two consecutive checks into a `tick.stale` incident, then pulls due incidents from `ops_events` (`src/lib/services/ops-alerts.ts`) and sends them: one alert per incident key, a reminder after 6 h while open, more than 3 due at once folded into one digest, at most 10 messages an hour (critical still goes out), scanner noise excluded, a daily digest of open incidents at 07:00 UTC. Platform stop / hold / pause changes push an alert through `alertControlChange()` right after they commit. Each alert key is claimed in `ops_alert_state` before sending; every message is logged in `ops_alert_deliveries`. The console's Providers page shows a topic- and token-free status and a "Send test alert" button.
**Reasoning:** PC-07 recorded failures, but nobody was told (X10: no alerting at all). Pulling from `ops_events` keeps every raiser unchanged and lets one claim-based dispatcher enforce dedupe, the budget and the digest across processes. A timer, not a queued job, so a lost Redis or a stuck BullMQ worker cannot silence the alert about it. On ntfy.sh the topic name is the credential, so it lives in env, is never rendered, and failures are scrubbed of it.
**Alternatives rejected:** Sending from inside `raiseOpsEvent` (every raiser would pay an HTTP call, and dedupe/budget would need the same cross-process state anyway); the webhook URL in `platform_secrets` with Telegram/Slack/JSON formats (the owner chose ntfy via env; the sink is one module, `src/lib/ops/ntfy.ts`, if another is ever needed); a BullMQ repeatable for the watchdog (dies with Redis, the thing it should report); email (PC-16).

### 2026-10-02 — Send-failure model, atomic 'sent', a stuck-work reaper and cross-process Cancel (Phase 1, PC-10)
**Decision:** A failed queued send is classified (`src/lib/mail/send-failure.ts`, on top of Phase 0's `classifySmtpError`): `transient` (SMTP 4xx, no reply) retries with exponential backoff up to 5 attempts, `local` (before the SMTP submission: translation, DB) and `unknown` up to 3, `sender_auth` holds the entry behind the failing mailbox, `recipient_hard` and `policy` fail; only `recipient_hard` ever suppresses. `sendMessage` tags the errors it throws instead of wrapping them (WeakMap / WeakSet): a provider failure carries its SMTP classification, and anything thrown after the server accepted the message is "after delivery" and is never retried. `sendMessage` gains `onPersisted(tx, message)`: the queue row turns `sent` in the same transaction as the `mail_messages` insert; post-insert audit and thread bookkeeping are best-effort. A paused mailbox holds its queue like a failing one. Failed, skipped and cancelled entries get Retry now / Requeue (any write role), which go back through the drain's own checks; the Errors-folder retry settles the draft's queue rows. A new tick, `ops.reaper.tick` (5 min, `src/lib/services/stuck-work.ts`), settles rows `sending` for 10 minutes (sent if a sent copy of the draft exists from the claim on, else failed `interrupted` + incident) and runs without progress for 15 minutes (pending 60). The runner keeps a heartbeat (`last_progress_at`) and reads `cancel_requested_at` on the same write between steps; it starts only `pending` runs and never overwrites a run that left `running` under it. internet_search ends `failed` when every query failed, `partial` when some did.
**Reasoning:** I007/I013/I014/I074: every exception made a queue row terminal, a restart mid-send left it `sending` forever (blocking the draft), a failure after the insert marked a delivered email `failed`, a paused mailbox failed its due queue after paying for the translation, and a run whose queries all failed showed green. Tagging keeps nodemailer's error objects intact for every existing caller. A database flag (not an in-process AbortController registry) is the only cancel signal that reaches a BullMQ worker in another process. Pending runs get 60 minutes because under BullMQ they can wait their turn behind others; the conditional claim means a reaped run never starts late.
**Alternatives rejected:** Wrapping send errors in a new error class (breaks callers and tests that read `responseCode`); retrying everything (a policy refusal or a dead address would be hammered); reusing `scheduled_send_at` for the backoff (loses the planned time the operator set); a `sending` timeout inside the drain (a second drain could double-send while the first is still alive; the reaper's conditional writes cannot); auto-resending interrupted rows (the email may have gone out).

### 2026-10-02 — Log noise cut at the source, and one daily retention tick (Phase 1, PC-35)
**Decision:** The autopilot tick visits only workspaces whose automation policy runs autopilot and that the automation gate lets through (`tickVerdict` in `services/automation-policy.ts`, PC-13 / PC-06). `runOnce` keeps its guard (the master switch, then the gate's refusal: `paused`, `hold:<id>`, `no_accountable_owner`, `plan_no_autopilot`, …) in `autopilot_settings.guard_state` and writes a `guard` row only when that state changes (an UPDATE conditional on the state the run read, in one transaction with the row); its return value still carries the guard every time. `syncInbound` audits only a sync that stored new messages. A new tick, `ops.retention.tick` (24 h, `src/lib/services/retention.ts`), deletes past their window: `autopilot_log` 30 days, `mail.sync_inbound` audit rows 30 days, read notifications 90 days (by created_at), resolved `ops_events` 90 days after resolving, `ops_alert_deliveries` and unused `ops_alert_state` keys 90 days, heartbeat rows of jobs no longer in the tick catalogue 90 days. Each policy is a named, batched delete (5,000 rows a statement, 200 statements a run); a failing policy does not stop the others but fails the tick afterwards (heartbeat + `tick.failed`). A run that deleted anything writes a platform `ops.retention.run` audit row. It is platform housekeeping and no pause, hold or stop gates it.
**Reasoning:** I066: a workspace with autopilot off logged a `guard skipped` row every 5 minutes (288 a day), so real autopilot activity scrolled off `/autopilot` within hours; the 2-minute IMAP tick audited every empty sync; nothing ever deleted from these tables. Recording the state on the settings row keeps the check O(1) and survives the log's own retention (a log lookup would rescan the log and re-log a state every 30 days). One tick with its own heartbeat makes retention visible and alertable like any other background work.
**Alternatives rejected:** Filtering guard rows out of the UI only (the rows still grow); reading the last guard row from `autopilot_log` (a backward scan per run, and lost after 30 days); per-workspace retention passes (archived workspaces would keep their rows forever; one pass per table uses one index); retention on `usage_log` (it backs token debits) or on other audit kinds (they are the record of what people did); unbatched deletes (the first run after months of growth would hold long locks).

**Reasoning:** Two diagnostic queries (the health check's rules and the assistant's snapshot) disagreed and missed live damage: failing mailboxes, the auto-suppression spike, mock search and a review queue the qualifier rejected went unreported, and the weekly check spent tokens with no opt-out and lost a week on any error (I129, I069, I095, I055, I057, I074, I182, I070). One engine with one contract means a fix PR adds a rule instead of another banner or query; a free sweep notifies on the live-damage rules without waiting for the weekly AI run.
**Alternatives rejected:** A materialised findings table refreshed by the tick (stale between ticks, and a second source of truth); notifying from every rule's source (most conditions have no event — a backlog or a mis-configuration just is); scoring per finding (two failing mailboxes would read as a dead workspace); an AI-written weekly summary (the findings already carry their copy; it would spend tokens to restate them).

### 2026-10-02 — One attention summary for every count (Phase 1, MOB-02; absorbs flow getAttentionCounts, the ia counts and AP-05a /api/shell/counts)
**Decision:** `getAttentionSummary(ctx)` (`src/lib/attention`) is the only source of the numbers that ask for a person: `review.open`, `review.needsReview`, `review.mine`, `drafts.approve`, `followUps.approve`, `replies.awaiting` / `replies.overdue`, `notifications.unread`, `support.unread` and `problems`, plus the automation pill and queue numbers (Ops' `getAutomationState`), the wallet, the health score and the problem findings. Each key has one written definition (`ATTENTION_KEY_DEFINITIONS`) and equals the default list of the page it opens (`/drafts` now opens on "Awaiting approval"; Today's Replies tab lists exactly the threads awaiting an answer, trash and spam left out). Every part loads on its own: one that fails is `null`, listed in `failed`, and sets `degraded`; every surface prints "—" for it, never 0 (`resolveNavCount`'s `unknown` option, `CountBadge`'s null). The sidebar counts (`nav-counts.ts`) are a pure projection of it (`navCountsFromAttention`); AppShell and Today share one computation per request (React `cache`); `GET /api/attention` serves it no-store with the pages' workspace resolution (401 signed out); `useAttention()` keeps the Sidebar current in the browser through one store per page (`store.ts`: poll every 60 s while visible, focus, `online`, `refreshAttention()` after a mutation, a service-worker `attention:refresh` message; no request on mount when the server rendered the summary). The findings come from the diagnostics engine read stale-while-revalidate (`maxAgeMs`, at most 5 minutes old, refreshed in the background; /health and the assistant still evaluate afresh), so a poll never waits for a full evaluation: p95 under 150 ms on the production-shaped fixture scaled 10x. The engine gains the live signals MOB-02 listed: `records.unqualified` (I077), `qualification.rules_fallback` (I025), `drafts.blocked` (approved but never queued, or no contact email) and autopilot step errors as a warning.
**Reasoning:** The sidebar, the Today tiles, the Today tabs and the assistant each counted on their own and disagreed (the Replies tab counted trashed and spam mail and every inbound message forever; the Review tile and badge used different queries; a failed load printed 0). Layouts do not re-render on client navigation, so the shell (and later the phone tab bar) needs the numbers from an endpoint, and that endpoint must be the same function the server render uses.
**Alternatives rejected:** Keeping `getNavCounts` and adding an API beside it (two definitions again); counting in the client from list endpoints (N requests, and the lists are paged); a counters table maintained by triggers (every writer must remember it, and a missed write is a permanently wrong badge); evaluating the findings on every poll (a full diagnostics run per tab per minute).

### 2026-10-02 — Tenant-safe sessions, workspace-carrying links and the expected-workspace guard (Phase 1, MOB-06)
**Decision:** The workspace is per SESSION. `sessions` gains `activeWorkspaceId` (FK to workspaces, ON DELETE SET NULL, in the migration's custom SQL like `users.activeWorkspaceId`), `createdAt`, `lastSeenAt` and `userAgent`. `resolveWorkspaceContextForUser(userId, isSuperAdmin, { sessionToken, userAgent })` picks, in order: the session's pointer (a membership, or god mode for a super-admin under the existing rules), the last-used `users.activeWorkspaceId` (what a new session starts in), the oldest membership (`created_at`, then id — the I042 ordering). The result is pinned on the session row when it differs, and `lastSeenAt` (at most every 5 minutes) and the User-Agent are kept in the same write. `getWorkspaceContext()` reads the session token from the request cookie (`src/lib/session-token.ts`; both Auth.js cookie names). `setActiveWorkspace` writes the switching session's pointer and the last-used value. `GET /go?ws=<id>&to=<path>` (`src/app/go/route.ts`) is the workspace-carrying link: it accepts only a relative path starting with a single '/' (no `//host`, scheme, backslash or control characters, no /go loop; else 400), switches THIS session only and only into a membership (403 otherwise — super-admins enter god mode through the audited switcher, never a link; archived refused for normal users), and answers 303 to the path with `?switched=<id>`, which the shell turns into a "Switched to …" notice and removes from the address bar. Notification links (`notificationHref`, from the stored in-app path and the row's workspace) and assistant answer links into another workspace than the page's (`assistantLink`) are built with `goHref` and rendered as plain `<a>` (never `next/link`, so never prefetched). The expected-workspace guard (`src/lib/workspace-guard`): the app shell provides the page's workspace (`WorkspaceGuardProvider`, in AppShell until MOB-03 moves it into `(app)/layout.tsx`); guarded forms carry `<ExpectedWorkspaceField/>` (`expectedWorkspaceId`), client callers pass `expectedWorkspaceId`, guarded fetches send `x-expected-workspace` (`useExpectedWorkspaceHeaders()`). `withWorkspaceGuard(id, action, { onMismatch })` and `withWorkspaceGuardRoute(id, handler)` resolve the session's workspace and, on a mismatch or a missing claim (fail closed), refuse before the action runs — form actions redirect to `/workspace-changed` (names both workspaces where the user is a member, offers to switch back through /go), value-returning actions return `{ ok: false, code: 'workspace_changed' }`, routes answer 409 `{ error: 'workspace_changed', detail }`. On a match the action runs with that context pinned (`runWithPinnedWorkspace`, AsyncLocalStorage), so every `getWorkspaceContext()` inside it returns the checked workspace even if the session moves mid-action. The registry (`registry.ts`) lists the 42 guarded actions — review decisions, Generate draft and bulk; draft approve / enqueue / reject / regenerate / archive / translate; follow-up approve / skip / reject; the reply, compose, suggest-reply and translate calls; every send-queue action; autopilot settings, product pause / resume, Run now and the workspace pause / undo / resume; buy tokens, subscribe and auto top-up; the assistant — and `src/tests/workspace-guard-mob06.test.ts` fails when one is unwrapped or a form or fetch that reaches it does not carry the claim. The guarded inline actions of /drafts/[id], /communication/follow-ups, /autopilot and /settings/billing moved to module-scope `actions.ts` files to be wrappable.
**Reasoning:** One pointer per user made a switch on a phone move the laptop's pages and badges into another tenant (VD-mobile-switch-workspace), and a tab left open on workspace A posted its Approve, Pause or Send into workspace B after a switch in another tab. Links from notifications and the assistant opened whatever workspace the browser happened to be in.
**Alternatives rejected:** A workspace segment in every URL (`/w/<id>/…`: every route, link and redirect changes, and MOB-03's route group would have to be redone); refusing a missing claim softly (a forgotten form would silently lose the guard — the static test plus fail-closed catch it at once); god mode through /go (a crafted link could drop a super-admin into a customer's tenant without the switcher's audit and banner); storing /go links in `notifications.href` (the path stays the record of where the notification points; the link is generated where it is shown).

### 2026-10-02 — Form controls styled once, Field primitives, email previews in a sandboxed frame (DS-10)
**Decision:** `src/styles/base.css` styles bare `input`, `select` and `textarea` everywhere (DS-06 had them inside `[data-ds]` only): the control-token heights as a min-height (36px, `--control-md` is 44px on a coarse pointer), 16px text on a coarse pointer, the input fill, the control border, a radius, the focus ring, invalid and disabled states, `color-scheme: dark`, a drawn select chevron (list boxes keep their rows), the native date and time inputs (no custom date picker), and the checkbox, radio and switch drawing. It still sits below legacy, so legacy's scoped restyles win where they exist; the restyles that only re-implemented a control with other metrics (`.form-grid`, `.inline-form`, `.leads-controls`, the review and draft forms, the recipe, provider, contact, mail-filter and crawl-plan forms, the login form, and others: 385 lines) were deleted, because a legacy `background` shorthand would also hide the drawn chevron. Embedded borderless inputs (the Cmd-K input, the contacts tag box, the inline pipeline number) keep their legacy look until their page wave. `src/components/ui/` holds the primitives: `Field` (label, one control, error and hint, wired by `useId` + `cloneElement`: `aria-describedby` lists the error, then the hint, then the control's own ids; stack or inline; full, num or auto width), `Input` (text-like types only), `Select` (default or plain), `Textarea` (rows decide the height), `SearchInput`, `Checkbox` and `Switch` (a native checkbox inside its own label, `role=switch` on Switch, so server actions read "on" with no JavaScript; the type requires a label or an aria-label; a `tone` of info, live or danger colours the checked state through `data-tone`). They are server-safe and restate the base values in `@layer components`, so a component control looks the same inside a legacy context. `EmailPreview` renders email HTML as the `srcdoc` of an iframe with `sandbox="allow-same-origin"` (no scripts; same-origin only so the component can size the frame to its content), a light mail-client canvas and a CSP that loads images only; the signature previews use it, and no component injects raw HTML into the page any more. Adopted on the settings forms Phase 0 touched (outreach, members, audit, CRM connection), the review date filter, the header workspace switcher (a plain small Select) and the contacts search; the page waves adopt the rest. Because base draws every checkbox and radio (`appearance: none`), `accent-color` reaches none of them: the checked colour is `--choice-on`, which base.css also takes from `data-tone` on a bare checkbox. The four legacy contexts that had picked a colour with `accent-color` (the red Remove step, the teal crawl, select-all and row checkboxes) carry `data-tone` instead, their dead `accent-color` lines are gone, and a test fails if legacy sets `accent-color` again.
**Reasoning:** Inputs were restyled in about 42 contexts with different heights, radii and padding, and every control outside them was a browser-default box (I153): on the 14 acceptance pages, at both widths, 212 of 246 controls sat off the token heights (19 to 42px), 82 on the browser default background, and 74 of the 123 on a phone had text under 16px (iOS zooms the page on focus below 16px). Injected signature HTML picked up the app's stylesheets, so the preview was not what a mail client shows, and a pasted `<img onerror>` ran as the app.
**Alternatives rejected:** Keeping the scope and migrating page by page (every unstyled control stays broken until its wave); `height` instead of `min-height` in base (a legacy rule with padding would clip its text); enforcing 16px text from the utilities layer (it would override every component's own sizing); a custom date picker (the native one is accessible and localised); a Shadow DOM preview (shares the document's script context and still needs a reset); `sandbox` with `allow-scripts` (with `allow-same-origin` the frame could run as the app).

### 2026-10-02 — The workspace frame is mounted once, by the (app) route group's layout (Phase 1, DS-07; absorbs ia:F-09, MOB-03, AP-05a)
**Decision:** Every workspace page lives in the route group `src/app/(app)/` (URLs unchanged: a group is not a URL segment), and `src/app/(app)/layout.tsx` renders `AppShell` once for all of them; no page renders it (a test fails if a file under `src/app` other than the layout imports it). `/admin` keeps its own layout and AdminShell; the landing page, `/pending`, the `/dashboard` and `/inbox` redirect stubs, `/go`, the dev gallery and the root error probe stay outside. The move is `scripts/codemods/app-route-group.mjs`: re-runnable (`git mv` of the 20 folders, a rewrite of every `@/app/…`, `src/app/…` and `app/…` path reference in src/, e2e/, scripts/ and docs/ — never TODO.md —, unwrapping a page's `<AppShell>` into a fragment), a second run is a no-op, files added under an old folder later are moved one by one and a file in both places stops for a hand merge; `--check` reports what is left and a test runs it on the repository. `getShellState()` (`src/lib/shell/state.ts`, request-cached) resolves the frame once per layout render and decides its state: signed out → `/`, an account waiting for approval → `/pending`, no workspace → a bare frame (brand header, email, Sign out) in which every workspace page answers with `<NoWorkspaceState/>` in place (list and settings pages; detail pages still send the person to their list), a resolution failure → the same bare frame and the page's own error, a workspace → the full frame for THIS session's workspace (MOB-06's expected workspace, provided once to every page). The frame's numbers (sidebar and area-tab badges, the bell, the account menu) are client islands over `<ShellAttentionProvider>`, which holds the layout's attention summary as the seed and keeps it current with `useAttention()`; a summary for another workspace never becomes the frame's numbers. The server-rendered rest of the frame changes when the layout renders again: a server action's response re-renders it (a redirect from an action renders the whole tree; `refreshChrome()` = `revalidatePath('/', 'layout')` does it for actions that return, and `withWorkspaceGuard` calls it for every guarded decision — `GUARDED_ACTION_CHROME` classifies each id, value-only actions such as translations do not refresh), and `<ShellRefresher/>` calls `router.refresh()` when the tab comes back after 5 idle minutes and once per new automation state the polled summary shows (pause, hold, platform stop: within a poll, or at once on focus). A summary for another workspace (a switch in another tab of the same browser) shows `<WorkspaceDriftNotice/>` with a Reload and never refreshes the frame on its own. The assistant panel is rendered with `key={workspaceId}` and the palette with a workspace key, so a switch or god mode starts both afresh; the account menu closes on navigation. `(app)/error.tsx` and `(app)/not-found.tsx` render their cards inside the frame. `ENABLE_TEST_ROUTES=1` adds `/test-only/shell-error` (a workspace page that throws) and a per-cookie frame-render counter (`/api/test-only/shell-renders`) for e2e/app-shell.spec.ts; both are 404s otherwise.
**Reasoning:** With AppShell rendered by each page, Next remounted it on every navigation: the "Ask the platform" conversation, Cmd-K's entity cache and the sidebar state were thrown away, and the session, workspace list, counts and notice queries ran again for every page (I053). A layout persists across client navigation, which is what keeps the conversation — and also why the frame can no longer rely on being re-rendered: numbers have to be live on the client, decisions have to re-render the frame explicitly, and a tenant switch in another tab has to be said rather than silently mixed into the page.
**Alternatives rejected:** Persisting the transcript in sessionStorage with the per-page shell (the queries and the remount stay, and the palette and sidebar state still reset); moving the shell into the root layout (the landing page, /pending and the console would need to opt out of it); polling the shell on every pathname change (AP-05a; costs a request per click for numbers the store already polls, and ia:F-09 rules it out); refreshing the frame silently when the browser's workspace changed in another tab (a page that swaps tenants under the pointer can take a click meant for the workspace the person was looking at — MOB-06's guard keeps refusing the stale page's actions instead); hand-moving the 59 pages (other branches could not replay it).
